## How the images are read back

As mosaicod serves a topic to its clients:

1. **Before the client asks, each format's images are already stored on the server.** They are the video's frames turned back into each format ([the server's results](../server/README.md)), and each format is kept as one topic, `camera/images/<format>`: one Parquet file with a row per image, in capture order, holding its capture time (`timestamp_ns`, as the client uploaded it), its `format` and its bytes (`data`, ZSTD-compressed), as mosaicod stores an image topic. This is done once, ahead of the fetch, and is not in the times below.
2. **`GetFlightInfo`: the client asks what it can read.** It sends a `GetFlightInfoCmd` with the sequence's locator, and the server answers with one endpoint per topic, so one per format. Each endpoint carries:
   - a **ticket** (`TicketTopic`): the topic's locator, which the client hands back in `DoGet` to say which topic it wants;
   - **metadata** (`TopicAppMetadata`): the format, the frames' size, and the topic's rows and bytes, which the client can read without downloading anything.
3. **`DoGet`: the client asks for one topic, and the server sends its images back, a few per message.** It tries to keep each message under 25 MiB, without ever cutting an image in two (see the note below):
   - **Before any image, it sends one message that describes the table**: its columns and what each holds (`timestamp_ns`, a 64-bit integer; `format`, text; `data`, bytes). The messages after it carry only the values, so the client needs this description to know which bytes are the timestamp and which are the image. It comes once per stream, which is why each format has one message more than its image messages.
   - **It reads a few images at a time** from the topic's file: about as many as fit in 25 MiB. Images of 8 MiB are read 3 at a time; an image over 25 MiB is read alone.
   - **If a group is still over 25 MiB, it splits it into smaller ones.** It can only cut between two images, never through one: each image is one row of the table, and the split moves whole rows. So an image always travels whole, in a single message, never half in one and half in the next, and an image over 25 MiB gets a message of its own, as big as the image. The split can also go further than needed: 3 images just over 25 MiB become 3 messages of one image each, not 2 + 1.
   - **It sends each group as one message**, compressed with LZ4 as mosaicod does, or not (both are measured; compressing does not change the messages).

   What this gave for each format, uncompressed (LZ4 gives the same messages):

   | Format | Average image | Largest image | Images read at a time | Images per message | Largest message (image bytes) | Messages (with the one describing the table) |
   |---|---|---|---|---|---|---|
   | Raw I420 | 50.6 MiB | 50.6 MiB | 1 | 60 × 1 | 50.6 MiB | 61 |
   | zstd | 9.7 MiB | 10.9 MiB | 2 | 30 × 2 | 20.8 MiB | 31 |
   | AVIF (lossless) | 6.4 MiB | 7.2 MiB | 3 | 3 × 3, 51 × 1 | 18.8 MiB | 55 |
   | FFV1 | 4.9 MiB | 5.4 MiB | 5 | 24 × 2, 12 × 1 | 10.5 MiB | 37 |

   Some groups were split even with less than 25 MiB of images: the server counts the memory a group takes up, which is a little more than its images.

> [!NOTE]
> **25 MiB is a soft maximum; 512 MiB is a hard limit.**
>
> - **25 MiB is a soft maximum** (mosaicod's). Many medium messages, rather than one huge one, let the client start on the first images sooner, and neither side has to hold a huge message in memory. The server goes over 25 MiB only when a single image is larger, since it never cuts an image in two, and it never pads a message to reach 25 MiB. Here the largest message was 50.6 MiB: one image alone.
> - **Both ends of a gRPC connection cap the size of a message.** The sender refuses to send a larger one, and the receiver refuses to accept it, failing the whole stream. By default a gRPC client accepts at most 4 MiB, less than most of these images. So the client raises its cap, its *receive limit*, to 512 MiB: the most mosaicod will ever send (`GRPC_MSG_MAX_SIZE_BYTES`). Whatever mosaicod sends, the client can take.
> - **So no image can be over about 512 MiB.** Every message carries at least one whole image, so an image larger than that could never be sent back. Taken to the extreme, 512 MiB is the largest image mosaicod can serve: about 10 times the 50.6 MiB of a raw 8K frame, so far beyond any image here.
> - **Uploading has its own, smaller cap**: the server accepts messages of at most 50 MiB by default (mosaicod's decode limit), which raw's images exceed.

4. **The client** saves each image as a file and decodes it with the server's own readers (the `formats` crate): one at a time, then 4 at a time. Every image of an exact format must decode to the same frame as raw's, and every image's `timestamp_ns` must be the one uploaded, or the fetch fails.

Client and server run on the same machine, over loopback: the network is not a bottleneck, and the two share the CPU. Each time is one run.

## What was measured

- **Receiving**: from the `DoGet` call to the end of the stream, for all the images: the server reading the Parquet file (and undoing its ZSTD), compressing with LZ4 or not, gRPC over loopback, and the client decoding the Arrow IPC messages (and undoing the LZ4).
- **First image**: how long the client waits before the stream starts: from its `DoGet` request to the first image in its hands (the image's bytes and its `timestamp_ns`). In between, the server reads the first batch from the topic's Parquet file (undoing its ZSTD) and encodes it (with LZ4 or not), the message crosses loopback, and the client decodes it back into a record batch. Decoding the image into a frame is not counted; a batch can carry up to 3 images, which arrive together. Raw's first message is a whole 50.6 MiB image, so it starts later than the others.
- **On the wire**: what the `FlightData` messages carried (IPC headers and bodies), against the image bytes themselves.
- **Saving** each image as a file, and **decoding** the files to frames, one at a time and 4 at a time (the OS keeps the files in its cache).

`GetFlightInfo` took 3.6 ms uncompressed and 2.9 ms with LZ4: negligible.

## What it shows

- **LZ4 shrinks Raw I420** from 3,038 to 1,042 MiB on the wire (2.9x), and receiving takes 4.99 s against 2.50 s uncompressed: over loopback, compressing and decompressing cost more than the bytes saved; on a slow link, where the bytes dominate, it would pay.
- **LZ4 doesn't shrink zstd, AVIF (lossless), FFV1, PNG (16-bit RGB), JPEG (quality 100)**: their images are already compressed, so Arrow's IPC writer keeps their buffers as they are (it does when LZ4 doesn't make one smaller), and the streams carry the same bytes. It still costs time, as the writer compresses every buffer before keeping it as it is: zstd 0.26 s uncompressed, 0.49 s with LZ4; AVIF (lossless) 0.27 s uncompressed, 0.36 s with LZ4; PNG (16-bit RGB) 0.85 s uncompressed, 1.19 s with LZ4; JPEG (quality 100) 0.54 s uncompressed, 0.62 s with LZ4.
- **Receiving is fast against decoding** for every compressed format: zstd 0.26 s to receive, 0.67 s to decode 4 at a time; AVIF (lossless) 0.27 s to receive, 16.55 s to decode 4 at a time; FFV1 0.34 s to receive, 3.11 s to decode 4 at a time; PNG (16-bit RGB) 0.85 s to receive, 7.00 s to decode 4 at a time; JPEG (quality 100) 0.54 s to receive, 5.58 s to decode 4 at a time. Over loopback the client waits on its decoder, not on the stream (zstd arrives fastest, 2,231 MiB/s).
- **Raw is the slowest to receive** (2.50 s uncompressed): 3,038 MiB, one image per message (each over mosaicod's 50 MiB upload limit but within its 512 MiB download one), and the server undoes the Parquet ZSTD of every image.
- **Every image comes back with the capture time it was uploaded with**, to the nanosecond: the client checked each `timestamp_ns` of every format against its `timestamps.csv`, in both runs.
- **The exact formats arrive exact**: zstd, AVIF (lossless), FFV1 decoded on the client to the same 60 frames as raw, byte for byte, in both runs.

## Limits

- Loopback: no network between client and server, so receiving measures the server's reading and encoding and the client's decoding, not a link. The table above gives the link's share.
- Client and server share the machine: each slows the other a little.
- One run of each, files in the OS cache (see the server's limits).
