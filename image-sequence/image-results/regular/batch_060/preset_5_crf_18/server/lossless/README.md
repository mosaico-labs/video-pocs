# Lossless formats: regular_batch_060, preset 5 CRF 18

Generated by `scripts/image_formats.py` from the server's report (`server --extract-images`, [`images.json`](../images.json)); do not edit. Part of [the comparison of the image formats](../README.md), whose charts show these formats next to the lossy ones.

These formats keep the frames exactly as dav1d decodes them, 8-bit YUV 4:2:0, BT.709 in limited range, with no conversion. After writing each image, the server reads it back and checks it byte for byte against its frame, and stops if one differs: every one of the 60 images of every format here is exact. They differ only in size and speed: their RMS error and their butteraugli distance are 0.

Each format's README has its charts, frame by frame: the size, encoding and decoding time of each image, all the images against the AV1 video.

## What it shows

- **FFV1 is the smallest**: 4.9 MiB per image, 10.4x smaller than raw, encoded in 67 ms and decoded in 47 ms. It is not an image format a client opens on its own, though: reading it takes FFmpeg (or another FFV1 decoder).
- **zstd decodes fastest** of the compressed formats (32 ms), with a decoder available almost everywhere, but its images are 2.0x the size of FFV1's.
- **AVIF (lossless) is by far the slowest**: 564 ms to encode and 549 ms to decode one image, 12x FFV1's decoding, for images 1.3x as large. Lossless AV1 coding at this size is simply expensive: in a separate test on one 8K frame (of `rate-change/batch_060/preset_9_crf_30`), splitting the image into 4x4 tiles, so that dav1d can decode them in parallel, barely sped up decoding (0.58 s to 0.52 s); the preset did not change the image (presets 8 and 10 gave the same size and time). Its advantage is being a standard image file that any AVIF reader opens. One image keeps only a few cores busy, so 4 at a time write the whole sequence 2.0x faster and read it back 2.5x faster ([details](avif/README.md#several-images-at-a-time)).
- **Raw's 50.6 MiB frames**: a frame is over the 50 MiB a message may carry to the server (mosaicod's default decode limit), and served back to a client it comes in one `DoGet` message, which may carry up to 512 MiB. The compressed formats are well within both.
- zstd's first images take longer to decode (49 ms, against a median of 32 ms): a warm-up, included in the means.
- FFV1's first images take longer to encode (95 ms, against a median of 58 ms): a warm-up, included in the means.
