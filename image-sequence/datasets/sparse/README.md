# sparse: A few frames far apart, with uneven gaps

The camera keeps only a few frames, far apart and unevenly: frame 0, then
one 10 frames later, then one 20 frames after that, and so on in turn
(0, 10, 30, 40, 60, 70, ... up to 280). Each image keeps the ideal capture time of
its frame, so the gaps are 333.7 ms and 667.3 ms. This is what a camera
records when it saves a frame only now and then: on an event, or on a slow
timer. With 300 frames in the sequence and 2 kept in every 30, it has
20 images; `batch_003/` (frames 0, 10, 30) is the smallest uneven case.

**Why no constant frame rate fits:** one slot every 333.7 ms fits the short
gaps, but each long one leaves an empty slot that only a repeated frame can
fill; one slot every 500.5 ms (the mean gap) gives each image a slot of its own,
but moves frames by 166.8 ms. The server encodes it at a variable frame rate,
each frame at its capture time; `batch_002/`, with a single gap, is still
evenly spaced and becomes constant (3000/1001).

## Numbers

| Images | Time between frames (min) | Time between frames (max) |
|---|---|---|
| 20 | 333.7 ms | 667.3 ms |

## Files

`batch_001/` holds the first image, `batch_002/` the first two, and so on up
to `batch_020/`, which holds all of them. Each folder has a
`timestamps.csv` with one row per image:

```
image,timestamp_ns
datasets/ImageSequence/001/000_8K.png,1767225600000000000
```

- `image`: the PNG's path, relative to the repository root, in
  `datasets/ImageSequence/001/` (8192x4320 PNGs, not copied here).
- `timestamp_ns`: the capture time, in nanoseconds since the Unix epoch; the
  ideal first capture is at 2026-01-01T00:00:00Z.

## In the video

The server encodes `batch_020/` at a variable frame rate: one frame per
image, each at its capture time, with no frame rate declared (see
[Constant or variable frame rate](../../README.md#constant-or-variable-frame-rate)).
The first capture time, 1767225600000000000 ns, is written once as the
`CAPTURE_START_NS` tag, and each frame's timestamp is its capture time minus
that one, rounded to the millisecond (FFmpeg's Matroska muxer stores
milliseconds), so at most 0.5 ms off:

| # | Image | Capture time − first (ms, from the CSV) | Video timestamp (ms) | Shown for (ms) |
|---|---|---|---|---|
| 0 | 000 | 0.000 | 0 | 334 |
| 1 | 010 | 333.667 | 334 | 667 |
| 2 | 030 | 1001.000 | 1001 | 334 |
| 3 | 040 | 1334.667 | 1335 | 667 |
| 4 | 060 | 2002.000 | 2002 | 334 |
| 5 | 070 | 2335.667 | 2336 | 667 |
| 6 | 090 | 3003.000 | 3003 | 334 |
| 7 | 100 | 3336.667 | 3337 | 667 |
| 8 | 120 | 4004.000 | 4004 | 334 |
| 9 | 130 | 4337.667 | 4338 | 667 |
| 10 | 150 | 5005.000 | 5005 | 334 |
| 11 | 160 | 5338.667 | 5339 | 667 |
| 12 | 180 | 6006.000 | 6006 | 334 |
| 13 | 190 | 6339.667 | 6340 | 667 |
| 14 | 210 | 7007.000 | 7007 | 334 |
| 15 | 220 | 7340.667 | 7341 | 667 |
| 16 | 240 | 8008.000 | 8008 | 334 |
| 17 | 250 | 8341.667 | 8342 | 667 |
| 18 | 270 | 9009.000 | 9009 | 334 |
| 19 | 280 | 9342.667 | 9343 | **334** (the gap before it) |

- The image name is the frame's number in the 29.97 fps sequence, so its
  capture time is that number of frame periods after image 000: image 280
  is 280 × 1001/30000 s = 9342.667 ms after it.
- Frames 0 to 18 each last until the next one's timestamp. The file holds
  no duration for them: with no `DefaultDuration` in the track, Matroska
  defines a frame's duration as the gap to the next frame.
- Frame 19 has no next frame, so the server gives it the gap before it:
  9342.667 − 9009.000 = 333.667 ms, 334 ms rounded. The file holds it as
  the video's length, the segment `Duration`: 9343 + 334 = 9677 ms, the
  9.677 s that `ffprobe` reports.

This folder is generated by `image-sequence/scripts/build-timestamps.py`;
see [the overview](../README.md).
